## Introduction

Text in the client area comes from two layers. Most of it is WHMCS's own:
every string WHMCS ships is translated by WHMCS language files, and Hadrian
uses those strings wherever one exists. The second layer is the theme's: copy
that has no WHMCS equivalent - the dashboard cards, the store pages, the
locale chooser itself - lives in the theme's own language file at
`templates/hadrian/core/lang/english.php`, about 1,900 strings organised into
named groups.

The theme ships in English. Everything below is about the second layer: how
those strings follow the visitor's language, how to reword any of them without
your edits being lost to updates, and how to add a full translation.

:::info WHMCS strings are translated in WHMCS
The theme deliberately never duplicates a string WHMCS already provides, so
WHMCS-native text - invoice labels, order statuses, form fields - is translated
the WHMCS way: install the language under `/lang/` and use
`/lang/overrides/` for edits. See the WHMCS Localisation documentation for
that layer. This page covers the theme's strings only.
:::

## How the active language is chosen

WHMCS decides. A visitor picks a language (any link carrying `?language=`),
WHMCS stores it in the session, logged-in clients get their profile language,
and everyone else gets the system default from **Configuration -> System
Settings -> General Settings -> Localisation**. Hadrian reads that decision on
every page - client area and order form both - and loads its own strings to
match. There is nothing to configure on the theme side.

## The locale chooser

What visitors use to switch. The header shows a locale button - flag of the
active language, its name written in itself, and the active currency:

:::shot img/lang-locale-btn.png The locale button with French active. On Windows the flag renders as a letter pair; other platforms show the flag emoji.

Clicking it opens the combined language and currency modal:

:::shot img/lang-locale-modal.png Every language is named for its own readers - Deutsch, not "German" - and the active choices are highlighted.

Picking a language applies it with a `?language=` reload, so WHMCS itself
records the choice and every layer - WHMCS strings, theme strings, prices -
switches together. Currency works the same way through `?currency=`.

Three controls shape the chooser:

:::props
| Control | Where | What it does |
| --- | --- | --- |
| Hide Language Switcher | [Layout Manager -> Header](/client-theme/layout-manager/#header) | Removes the language half of the button and modal |
| Hide Currency Selector | [Layout Manager -> Header](/client-theme/layout-manager/#header) | Removes the currency half; with both hidden the button disappears entirely |
| Custom Language List | [Settings -> Language and SEO](/client-theme/settings/#custom-language-list) | Curates which installed languages the modal offers |
:::

On an install with a single active currency the currency section hides by
itself - no setting needed.

## Rewording any string - overrides

To change the theme's wording - one label, or fifty - use the overrides
folder. Files in it are yours: a theme update replaces the shipped language
files, but never touches `overrides/`.

:::steps
1. Connect to your WHMCS server over FTP/SFTP.
2. Go to `templates/hadrian/core/lang/` and create a folder named `overrides`.
3. Inside it, create a file named after the language it applies to - `english.php` for English.
4. Return only the keys you want to change, in the same nested shape as `english.php`.
:::

Find the string you want to change in `core/lang/english.php` - say the modal
title:

```php
// core/lang/english.php (shipped - do not edit this file)
'common' => [
    'localeChoose' => 'Choose language & currency',
],
```

Then override just that key:

```php
<?php
// core/lang/overrides/english.php (yours - survives every update)
return [
    'common' => [
        'localeChoose' => 'Language & billing currency',
    ],
];
```

Everything you leave out keeps its shipped value. The merge is per key, so an
overrides file with one line is valid.

Create one overrides file per language you run - `overrides/german.php`
changes the German wording, and so on.

:::tip New strings work too
An overrides file can also mint strings that never existed, using any new
group and key names. They become available to templates as
`{$hadrianLang.yourgroup.yourkey}` - useful together with
[template overrides](/client-theme/customize-pages/), which let you add markup
that renders them.
:::

:::warn A broken override is ignored, not fatal
Each override file loads inside its own guard. A PHP syntax error in one makes
the theme skip that file and carry on with the shipped strings - your site
never white-screens over a typo. If your override seems to have no effect,
re-check the file's syntax first.
:::

## Adding a language

The theme looks for `core/lang/<language>.php`, where `<language>` is the
WHMCS language name in lowercase - the same name as the WHMCS file under
`/lang/`. If the file exists, it is used; there is nothing to register.

:::steps
1. Make sure the language itself is installed in WHMCS (a `/lang/<language>.php` file exists and the language is active).
2. Duplicate `templates/hadrian/core/lang/english.php` as `templates/hadrian/core/lang/<language>.php` - for example `french.php`.
3. Translate the values. Never change the keys or the array shape.
4. Visit the site with that language active - the theme picks the file up immediately.
:::

Untranslated keys fall back to English one key at a time, so a partial
translation ships the translated parts now and the rest stays readable - you
do not have to translate all 1,900 strings before the file is usable. A
language with no file at all simply gets English.

:::info Your translation survives updates
Theme updates replace the files the theme ships - and the theme ships only
`english.php`. A `french.php` you created is not part of any update, so it
stays. For edits to the *shipped* English wording, use
[overrides](#rewording-any-string-overrides) instead of editing `english.php`
in place.
:::

## Translating menu items

Menu labels are content, not language-file strings - you write them in the
[Menu Manager](/client-theme/menu-manager/). Each item's editor has a
**Translate** disclosure offering one field per language (the same list the
locale chooser shows). An item's label resolves as: the visitor's language if
you filled it in, otherwise the WHMCS string when the item is in WHMCS-key
mode, otherwise the English custom label.

## Multi-language SEO

Two pieces, both already covered in depth elsewhere:

- Per-page SEO titles and descriptions accept a value per language - see
  [Writing SEO copy in every language](/client-theme/page-manager/#writing-seo-copy-in-every-language)
  in the Page Manager article.
- [Enable Alternate Links](/client-theme/settings/#enable-alternate-links)
  emits one `hreflang` tag per offered language plus `x-default`, so search
  engines index the right language for the right audience.

One nuance worth knowing: `hreflang` values must be ISO codes, and the theme
maps WHMCS language names ("french" -> `fr`) through a table covering every
language WHMCS ships. A custom language file with a name the table does not
know is silently left out of the alternate links - the page still works, it
just is not advertised to search engines in that language.

## The cookie bar

The cookie-consent message is admin-entered content with one field per
installed language - filled in under
[Settings -> Cookie Box](/client-theme/settings/#cookie-box). A language you
leave empty falls back to the system default language's message, then to the
theme's built-in string - so the banner is never blank as long as the default
language's message is filled in.

## The store pages

The store landing pages (SSL, SiteLock, CodeGuard and the rest) are theme
pages, and every word on them comes from the theme language file's `store`
group. Translating the theme file translates the store - there is no separate
mechanism, and WHMCS's Dynamic Field Translation is not involved.
